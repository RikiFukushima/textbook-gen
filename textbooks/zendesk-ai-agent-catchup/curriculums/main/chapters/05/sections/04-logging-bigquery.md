## このセクションで学ぶこと

- 「どのリクエストで何を参照し何を返したか」を1行の構造化ログに残す設計
- そのログを BigQuery に流すと、後の評価データセットにそのまま使えること
- この surface が「評価基盤ごと売る」に直結する理由

## 何を残すか — 1リクエスト = 1行の構造化ログ

4つ目の surface はログとオブザーバビリティです。ここでの目標はシンプルで、**agent が1回のチケット処理で「何を参照し、何を返し、どう扱われたか」を後から追える形で残す**ことです。

そのために、自由文のログではなく **構造化ログ**(決まったフィールドを持つ1行)にします。最低限、次のフィールドを1行にまとめます。

```json
{
  "ticket_id": "12345",
  "referenced_knowledge_ids": ["kb-018", "kb-072"],
  "generated_draft": "お問い合わせありがとうございます。...",
  "approval_result": "approved",
  "created_at": "2026-07-27T10:12:03Z"
}
```

- `ticket_id`: どのチケットの処理か
- `referenced_knowledge_ids`: RAG でどのナレッジを参照したか(根拠の記録)
- `generated_draft`: 生成した返信ドラフト
- `approval_result`: 人間がどう扱ったか(承認 / 修正 / 却下)

この1行があれば、「このチケットで agent は何を根拠にこう返し、人間はどう判断したか」が丸ごと再現できます。これは第01章で描いたプロトタイプ実装順の**⑥「ログを残す」ステップ**そのものです。

## どこに流すか — BigQuery に貯める

このログを **BigQuery** に流し込んでおきます。BigQuery は大量のログを貯めて SQL で集計・分析できる基盤なので、行数が増えても「承認率はどれくらいか」「どのナレッジがよく参照されるか」を後から自由に問い合わせられます。

実装としては、agent が1リクエスト処理し終えるたびに上記の1行を BigQuery のテーブルに追記するだけです。凝った収集基盤は要りません。

## なぜここに力を入れるのか — 評価基盤ごと売る

オブザーバビリティは苦手意識を持たれがちですが、この案件では**触れておく価値が特に高い** surface です。理由は、貯めたログがそのまま**評価データセットの素材**になるからです。

- `generated_draft` と `approval_result` が揃っていれば、「AI のドラフトが人間にどれだけ通ったか」を測れます。
- `referenced_knowledge_ids` が残っていれば、参照根拠の妥当性も後から検証できます。

つまり、日々の運用ログを貯めるだけで、第06章で扱う **評価データセットと段階リリース(シャドウ運用 / A-B)** の土台が自動的に育ちます。これが「単なる返信 bot」ではなく **評価基盤ごと売る** という提案につながります。最初のログ設計をここで押さえておくと、後の提案の幅が大きく変わります。

## まとめ

- 1リクエスト=1行の構造化ログに、ticket_id / 参照ナレッジID / 生成ドラフト / 承認結果を残す。
- そのログを BigQuery に流せば、SQL で承認率や参照傾向を分析できる。
- 貯めたログは評価データセットの素材になり、「評価基盤ごと売る」に直結する。
