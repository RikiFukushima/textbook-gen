## このセクションで学ぶこと

- Zendesk / LLM の API キーの置き場所を、環境変数と Secret Manager の2択で考える
- 環境変数の手軽さと、その弱点(ローテーション・監査)
- Secret Manager が受託案件で効いてくる理由

## API キーをどこに置くか

タイプ3の agent は、Zendesk API と LLM API を叩くために **API キー(シークレット)** を持ちます。これをコードに直書きするのは論外として、置き場所は実務上ほぼ2択です。

- **環境変数**: 実行環境に `ZENDESK_API_TOKEN=...` のように設定して読み込ませる
- **Secret Manager**: Google Cloud などのマネージドサービスにシークレットを預け、実行時に権限付きで取り出す

今回はこの2つの違いが分かれば十分です。細かい暗号鍵管理やローテーション自動化まで踏み込む必要はありません。

## 環境変数 — 手軽だが弱点がある

環境変数はとにかく手軽です。Vercel でも Cloud Run でも、設定画面に値を入れればすぐ使えます。プロトタイプの段階ではこれで十分動きます。

ただし弱点があります。

- **ローテーションが弱い**: キーを差し替えるたびに手作業で環境変数を更新することになり、複数環境があると漏れが出やすい。
- **監査が弱い**: 「誰がいつそのキーを見たか/変えたか」の記録が残らない。事故が起きたとき追跡できません。

個人開発なら許容できますが、顧客の Zendesk と LLM の課金キーを預かる受託案件では、この弱さがそのままリスクになります。

## Secret Manager — 集中管理・バージョン・権限

**Secret Manager** はこの弱点を埋めます。

- **集中管理**: シークレットを1か所にまとめ、アプリからはそこを参照する形にできる。
- **バージョン管理**: 値を更新しても過去バージョンが残り、差し替え(ローテーション)や切り戻しがしやすい。
- **権限管理**: どのサービスアカウントがどのシークレットを読めるかを制御でき、アクセス記録も残せる。

受託では「キーの管理をどうしているか」を顧客に説明できること自体が信頼につながります。特に顧客の LLM 課金キーを預かる場合、キーが漏れれば金銭的な被害に直結するため、「誰が読めるか」「いつ差し替えたか」を示せる状態はそのまま安心材料になります。プロトタイプは環境変数で始めてよいですが、**本番に近づけるなら Secret Manager へ寄せる**、という移行の道筋を頭に置いておいてください。

なお、環境変数か Secret Manager かは「どちらか一方」ではなく、段階の話として捉えるのが実務的です。検証の速さがほしい初期は環境変数で回し、顧客のキーを預かって本番運用に入る段階で Secret Manager へ移す、という順序で十分間に合います。最初から作り込む必要はありません。

## まとめ

- API キーの置き場所は環境変数か Secret Manager かの2択で考える。
- 環境変数は手軽だがローテーションと監査が弱い。
- Secret Manager は集中管理・バージョン・権限管理ができ、受託の本番運用で効く。
