## このセクションで学ぶこと

- 単発 Q&A なら単純な chain で足りること
- マルチステップ分岐・外部アクション・人間承認があれば LangGraph が効くこと
- 採用の分かれ目を「状態を保存して途中で止める必要があるか」で言語化する

## まず「本当に要るのか」を疑う

ここまで checkpoint・interrupt・グラフ設計を見てきましたが、最後に一歩引きます。LangGraph は状態・分岐・中断を扱うための道具で、そのぶん構成部品が増えます。**要らない場面で持ち込むと保守コストだけが増える**、いわゆる過剰適用になります。

分かりやすい線引きは「一直線か、そうでないか」です。ユーザーの質問に RAG で答えを1回返すだけ、というような **単発 Q&A** は、入力から出力へ一直線に流れる **chain** で十分です。State を保存する必要も、途中で止める必要もありません。ここに checkpointer やグラフを持ち込むのは大げさです。

## LangGraph が効くのはどういうときか

逆に、次のどれかが絡むなら LangGraph の出番です。

- **マルチステップの分岐**: 「十分なら承認へ、不十分なら再生成へ」のように、途中の結果で進路が変わる(03-03)。
- **外部アクション(副作用)**: Zendesk への書き戻しのように、後戻りできない操作を条件付きで実行する。
- **人間承認(human-in-the-loop)**: 途中で止めて人間の判断を待ち、その入力で再開する。

この案件が LangGraph を採用するのは、まさに3つ目の人間承認と2つ目の書き戻しがあるからです。「生成して終わり」ではなく「生成 → 止めて待つ → 承認されたら書き戻す」という流れは、chain では素直に書けません。中断のために状態を永続化する必要があり、それがそのまま checkpointer の存在理由になっています。

言い換えると、判断は機能の多さではなく「止めて待つ必要があるか」の一点に集約できます。分岐が1つあるだけなら if 文で書けますし、外部呼び出しが1回あるだけなら関数を呼ぶだけです。それらが **人間の判断をまたいで非同期に続く** ときに初めて、状態を保存して後から再開する仕掛けが要る。この案件はチケット対応という業務そのものが「AI の下書きを人間が確認して送る」という非同期の承認を含むため、LangGraph が素直にはまります。

## 注意点

- 「将来分岐が増えるかも」で先回りして LangGraph を入れるのは過剰適用になりがちです。**いま止めて待つ必要があるか**で判断します。
- 逆に、外部への書き戻しや人間承認があるのに chain で無理やり組むと、状態管理や再実行の防止を自前で作り込むことになり、結局 LangGraph の劣化版を再発明します。
- 道具の選択は固定ではありません。単発 Q&A で始めても、承認フローが要件に入った時点で LangGraph へ載せ替える判断があってよいです。

## まとめ

- 単発 Q&A は一直線の chain で十分。状態も中断も要らないなら LangGraph は不要
- マルチステップ分岐・外部アクション・人間承認のどれかがあれば LangGraph が効く
- 採用の分かれ目は「状態を保存して途中で止める必要があるか」
